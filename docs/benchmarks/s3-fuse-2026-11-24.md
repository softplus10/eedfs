# MinIO and mounted filesystem benchmark — 2026-11-24

Source: `56fd711`. These are actual mounted writable FUSE tests against a real
local MinIO server, using the encrypted header/inode/chunk formats. They are not
the earlier in-memory crypto benchmark. [Filesystem raw JSON](s3-fuse-2026-11-24.json),
[direct S3 raw JSON](minio-baseline-2026-11-24.json), [setup and limits](../s3-fuse.md).

## Environment and procedure

- Intel Core Ultra 7 155H, x86_64, 22 visible logical CPUs; no CPU affinity or
  container CPU/memory quota. Normal development host, not an isolated lab.
- Linux 6.12.0-211.67.1.el10_2.x86_64; rootless privileged Podman, Alpine/musl.
- Rust 1.100.0, release opt-level 3, thin LTO, codegen-units=1. FUSE 3 runtime.
- MinIO built using Go 1.27.3 from `RELEASE.2025-04-22T22-12-26Z` upstream source.
  It identifies itself as DEVELOPMENT.GOGET because this is a `go install` build.
  Public image/binary downloads were unavailable; no substitute S3 server was used.
- Standalone single-drive MinIO, HTTP loopback on 127.0.0.1:19000, one host;
  data and client staging files on the same XFS filesystem over dm-crypt/LUKS.
  This does not measure a physical NIC, WAN latency, TLS, or a distributed MinIO cluster.
- XChaCha20-Poly1305, 8 MiB writer chunks, 8 in-flight object tasks per commit,
  8 FUSE workers per mount; three separate filesystem processes/mounts for concurrency.
- Payload buffers are generated randomly before individual write timers; they are
  reused across syscalls, without application compression. SHA-256 is updated
  inside file read/write timings. Uploads include encryption and SDK checksums.
- One measured run per case, not medians. Order: 1 GiB direct S3 baseline,
  filesystem workloads, then 10 GiB direct S3 baseline. OS caches are uncontrolled.

Filesystem write timers include file open/create, local staging, SHA-256,
remote fsync, and close. Read timers start after open and include reads/checksums,
but exclude the inode lookup/open and close. The remounted client has no old
plaintext spool, but MinIO's OS cache is **not** dropped. Warm reads retain the
same open file handle and use the local plaintext spool, with FUSE direct I/O;
they are not repeated S3 downloads. Direct S3 GET validates every object's bytes
against the source buffer, without FUSE/encryption/local file staging.

## Results

| Case | Logical size | Seconds | MiB/s |
|---|---:|---:|---:|
| Direct S3 PUT, 8 parallel tasks | 10 GiB | 16.71 | 612.8 |
| Direct S3 verified GET, 8 parallel tasks | 10 GiB | 5.16 | 1986.0 |
| FUSE sequential write + remote fsync | 10 GiB | 34.93 | 293.2 |
| FUSE read after remount | 10 GiB | 46.78 | 218.9 |
| FUSE read, warm open handle | 10 GiB | 14.14 | 723.9 |
| FUSE write + fsync, 3 clients aggregate | 3 × 512 MiB | 2.61 | 588.9 |
| FUSE 4 KiB writes, one final fsync | 64 MiB | 0.37 | 174.6 |

- Three clients created and fsynced 60 separate 4 KiB files in one directory:
  **53.3 files/s**, 1.13 seconds. All contents verified from another mount.
- 32 random aligned 4 KiB overwrites, fsync after every operation:
  **10.68 operations/s**, 3.00 seconds. Final file contents verified.
- The 10 GiB write spent **10.03 s staging** and
  **24.90 s in remote fsync**. The uploader currently starts at
  commit, so these phases do not overlap. fsync includes chunk reads from the
  spool, encryption, bounded PUTs and conditional inode publication.

## Correctness evidence

- 41 default tests passed, plus 2 explicitly invoked real-MinIO tests; formatting,
  strict Clippy and the retained read-only FUSE mount smoke passed.
- Real-store tests checked create-only/ETag PUT conflicts, stale token rejection,
  bounded reads, wrong-password rejection, different writer chunk policies,
  COW overwrite, sparse gaps, shrink/re-extend zeroing, and directory CAS merging.
- Three real mounts checked cross-client visibility, nested directories, partial
  overwrite, truncate, sparse gaps, unlink and persistence after unmount/remount.
- Stale writers to the same inode returned EAGAIN; the successful writer's bytes
  remained intact. Three concurrent clients preserved all independent creates.
- The 10 GiB file's complete SHA-256 matched after remount and on a second warm
  read. All three 512 MiB outputs matched when read from another client.
- All benchmark processes completed successfully; mounts were cleanly unmounted.

## Interpretation and limits

The complete filesystem path is slower than direct S3 on this host. This
prototype adds local plaintext spool I/O, FUSE crossings, object encryption,
metadata requests and serial staging/commit phases. The data demonstrates that
the current path leaves performance available; it does not prove which individual
cost dominates without profiling. In particular, a remounted read downloads and
decrypts chunks into the local spool before satisfying reads. The warm-handle
result avoids that remote/decrypt stage.

The 4 KiB random-write case exposes chunk amplification: each changed 8 MiB
writer region is re-encrypted/uploaded, even for a 4 KiB edit. For these aligned
edits, that is 2,048× payload write amplification before inode metadata. Current
cache invalidation/prefetch can add further reads. This is a property of the
prototype's fixed writer policy, not a measured general S3 IOPS limit. The
variable-size reference format alone does not implement an adaptive chunker.

Three-client independent-file writes scale to about 589 MiB/s aggregate here,
while shared-directory creation and same-file contention have different costs.
The test does not provide same-file merge, atomic multi-client append, full
POSIX metadata/rename semantics or safe reclamation. Old/unlinked/staged objects
remain until an external cleanup of this disposable test store. No cluster or
provider-wide scalability claim follows from this single-host run.

## Reproduce

See [S3/FUSE setup](../s3-fuse.md) for MinIO and credential configuration. With an
existing disposable bucket and a private password file:

```sh
cargo build --release --locked --bin eedfs --example s3_bench
cargo test --locked --test volume_minio -- --ignored --test-threads=1
target/release/examples/s3_bench --mib 10240 --jobs 8
python3 scripts/bench-s3-fuse.py --binary target/release/eedfs \
  --password-file /private/password --work-dir /tmp/eedfs-bench \
  --output /tmp/eedfs-result.json --benchmark --large-mib 10240
```

The runner creates a unique prefix, never overwrites an existing volume, and
unmounts on exit. Remote objects are deliberately not deleted by the runner.
